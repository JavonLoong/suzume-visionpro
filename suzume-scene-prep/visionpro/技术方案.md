# 实体白门与门后世界的适配结构

本阶段已经完成内容与工程适配。实验室可使用 Mac 和 Apple Vision Pro，设备阶段从现有 Xcode 工程继续。

## 实体树与坐标

```
RealityView
└─ SuzumeDoorwayRoot（位置、绕 Y 旋转、等比缩放）
   ├─ DoorwayWorld / WorldComponent
   │  ├─ DreamWorld.usdz（默认仅通过门户可见）
   │  └─ Character.usdz（门后 2.7 m，面向门口）
   ├─ DoorwayAperture / ModelComponent + PortalMaterial + PortalComponent
   ├─ DoorFrame.usdz（可见校准参考）
   └─ DoorFrame clone / OcclusionMaterial（与可见参考互斥）
```

门洞为四顶点网格，顶点 Y 范围 0～2.1，X 范围 ±0.439459，Z=0，法线朝 +Z。其原点是门槛中心，和目标世界的原点一致。位于 +Z 一侧的用户向 -Z 看入门后；门户设置 `.clippingMode = .plane(.positiveZ)`。不启用跨门实体模式。

模型源坐标为 Blender Z-up；先减去源门槛中心，再等比缩放，最后由 USD 导出器转换为 Y-up。源门槛中心、源开口和缩放因子写入 `AssetManifest.json`，Swift 从同一清单读取参考尺寸，避免另一套手填比例。

## 材质与实时预算

花海包保留约 37.8 万个三角面，角色为 91,573 个三角面，门后可见内容合计约 46.97 万个三角面。当前是待测预算，不是已达到头显帧率的承诺。植物数量由源实例数据确定性抽样，花与茎共用索引；没有用平面图片代替近处花海。

角色由混元 3D 四视图重建。Blender 近景母版组合 500K 全身和 1.5M 专用头，共 1,916,499 个三角面；Vision Pro 版组合两个 50K 结果，并把贴图压到 2K。两档资产用途明确分开，近景母版不打包进应用。

源天空的自定义节点和 Cycles 体积云不直接传给 RealityKit，改为远景全景纹理。独立烘焙场景只链接天空、远景云和灯光，避免源角色的可见性驱动把角色烘焙到天空。源低空体积雾和已裁切的角色片段暂不纳入资产。

草地颜色以源材质烘焙，门框与门扇保留原 UV 和源贴图并转换为基础 PBR。应用把远景天空设为 UnlitMaterial，避免背景同时接受光照；花草与地形使用从同一全景生成的 IBL。灯光和材质最终效果需 RealityKit 检查。

## 对齐与遮挡的边界

当前通过中文面板手动调节门槛位置、绕 Y 朝向和统一比例。对齐一扇直立门时，以四个内角和门槛为参考。参数可保存，但 immersive space 的原点可能改变，因此保存数值不等于恢复真实世界锚点。

“仅作遮挡”使用已知的门框模型和 OcclusionMaterial；它不会自动识别人，也不会知道实体门扇是否在运动。关闭的实体门扇不在当前测试流程内，独立 `DoorLeaf.usdz` 为后续内容资产，不暗示已有门扇跟踪。

下一阶段有设备后，再选择 ARKit 图像／物体定位或人工锚点方案。只有定位方式、门的活动规则及跨门行为确认后，才扩展交互，避免把尚未确认的体验写死。

## 验收顺序

1. Xcode 模拟器构建，修正实际编译器诊断；进入、取消、退出、缺失资源和重复进入均正常。
2. 检查两个世界、门户开口与贴图朝向；通过观察位置变化确认不是固定平面影片。
3. 头显上对齐实体门内四角；从左右、远近和不同眼高观察，检查漂移与边缘裁切。
4. 确定实际遮挡方案并测试门框、门扇、行人的关系。
5. 测试实际帧时、内存和持续运行，再调整植物数量、贴图尺寸和材质。

本机 HTML 只覆盖第 2 步的几何预检，不模拟 RealityKit 或 ARKit。
